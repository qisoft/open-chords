# Open Chords JSON export

The public domain boundary is `captureJsonExport`, `parseJsonExport`, and `serializeJsonExport`. Capture copies and freezes the committed Active View before main opens the native save dialog. The versioned `current` and `original` profiles share Original assertions and the Effective Timeline; only declared presentation transforms differ. Selected lyrics, occurrence identity, timing, attribution, notices, confidence, and user authorship are included automatically. Support provenance uses typed references and benchmark hashes; free-form claim descriptions and operational alignment recipes are omitted with explicit Receipt entries. Authorship references and anchors are validated against retained entities and selected lyric occurrences.

The portable snapshot uses `format: "open-chords/json-snapshot"` and schema version `1.0`. It is deliberately distinguishable from the persisted `open-chords/project` contract: it cannot be opened as a backup or silently treated as a complete Project. Its JSON Schema is generated by `pnpm contracts:schema` and checked by CI. The byte fixture is independently specified with sorted object keys, two-space indentation, UTF-8 and a terminal LF; formatting tools exclude it to preserve the canonical vector. A separate Ajv Draft 2020-12 validator checks the published schema without calling the application's parser.

Main owns `exports.perform`, the native picker and all paths. Requests contain only a Project identity, expected saved revision and profile. Receipt summaries expose a basename and hashes, never the private destination. Recording a Receipt commits Project-owned records against the current Library head, preserving any musical edits made after capture.

## Publication and recovery

1. Validate and serialize the captured snapshot, bounded to 32 MiB.
2. Obtain an explicit native destination. Reject application/Library state, non-JSON names, links, linked parent directories and non-regular targets.
3. Persist the recovery directory entry in its parent, then a private recovery intent and flush it; write and flush a uniquely named sibling staging file.
4. Recheck destination identity, Library root and cancellation, then atomically rename the complete staging file to the destination and flush the directory.
5. Append an immutable, idempotent Receipt to the Library, then remove the recovery intent.

Cancellation before publication preserves the previous target. Publication is the cancellation boundary: afterward the operation completes or reports `receipt_pending`. A target file and Library record cannot be one filesystem transaction. If Receipt publication fails, the UI explicitly reports the full file plus pending recovery; startup or Retry Receipt recovery verifies the output hash and appends the same Receipt. Recovery never recreates or overwrites a target. Changed/missing outputs without a completed Receipt remain pending for investigation; unknown or malformed recovery records are retained. Library relocation does not allow a pending export to attach to another root.

The destination checks are best-effort protection against link substitution with identity rechecks; they do not claim an OS-anchored write against an actively racing process that can rename parent directories. The application's private state and trusted main remain required boundaries.

## Verification and remaining acceptance

- Public tests cover independent canonical bytes, immutable capture, later edits, semantic link/transform corruption, operational recipe exclusion, native-picker cancellation, protected/stale requests, existing-target preservation and Receipt recovery after an interrupted Library commit.
- The renderer test uses the real main/IPC/domain/filesystem/Library and replaces only the external picker result. It proves save, cancellation and Receipt reopening after process restart.
- The installed ZIP test loads a Receipt created through the public service, verifies the bounded named capability and reopens the Receipt panel. It does not claim native save-dialog interaction.
- Local macOS full validation passed on 2026-09-09 (445 unit tests and 33 renderer tests before the additional independent-schema test; two existing opt-in tests skipped). The macOS installed Receipt test passed.
- The actual native save-dialog pass is **pending**. The installed macOS application launched, but CUA could not attach: path lookup timed out after 120 seconds and bundle-ID lookup timed out after 20 seconds. No save/cancel/write-error observation is inferred from those attempts. Interactive Windows 11 is unavailable, as previously established. Hosted Windows tests do not replace this user-confirmed native boundary.

For the native pass on each platform, export the seeded repeated-lyrics Project with both profiles, cancel a second save, exercise an unwritable destination and overwrite an existing JSON file. Verify the previous target survives any pre-publication failure, no partial target is reported as successful, the Receipt hash matches the final bytes, and the Receipt is available after restarting the installed application. Preserve platform/build and observed results with the issue before closing acceptance.

## Review

The two-axis review found one durability issue (the newly created journal directory needed a parent-directory flush) and two semantic issues (unrestricted Support Claim descriptions and unchecked authorship anchors). All three were fixed and verified by the respective reviewers. The focused export suite now has 19 passing tests, including real POSIX staging-write denial; Windows uses the cross-platform target-rejection tests and retains its separate native write-error gate.
